# Engineering roadmap

Proposed work, not shipped behavior. The first release candidate is single-node, one native wire protocol, one streaming and one unary endpoint, and two deployments of the same protocol. Two lanes prove deployment fallback, not resilience to losing an entire provider.

**Delivery status:** M1 passed its engineering gate; the [reader decision and replay instructions](m1-results.md) identify the verified implementation. The [agent working agreement](../AGENTS.md) defines focused subagent assignments, effort selection, minimal context and independent verification.

### Constraints for intermediate builds

- **Separate routing from socket ownership without adding a hop.** Routing takes a pinned revision and explicit eligibility inputs; it neither owns a socket nor forwards individual chunks. The request coordinator owns grant checks, winner election, commit and cancellation. The transport attempt owns its socket and byte credit. Keep these boundaries local in M2; an eventual placement decision changes where *new work* starts. An already committed stream stays with its owner or ends incomplete.
- **Measure where connection time goes.** When qualifying the serving path, distinguish policy/queue time, connect/TLS, warm reuse, time to first meaningful output and time spent blocked by the downstream writer. Compare like-for-like workloads. A network split is not automatically cheaper or more resilient.
- **Leave a seam for multi-model policies, not a speculative orchestration engine.** Keep deployment, model capabilities and policy revision distinguishable; keep one request deadline and an explicit aggregate attempt/exposure budget; attribute outcomes and known/unknown usage per attempt. Later escalation, racing or fusion needs its own authorization, compatibility, privacy and evaluation gates. None can silently replace an already committed native stream. M2 still has one protocol, two same-protocol deployments and no model composition.

**Evidence with each change:** pin build, input, SDK and fixture; provide one rerun command, expected and observed client outcome, upstream counters and limitations. Deterministic and short real-socket cases belong on PRs; wide SDK/fault profiles run separately from the dedicated-host soak. A sandbox observation is evidence about gateway behavior under the supplied fault, not about a provider’s bill or capacity.
